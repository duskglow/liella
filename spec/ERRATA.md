# Spec errata and gaps

Found while deriving the plan and the scaffold from `glibc-functional-spec.md`. The spec stays
the only source of truth; these entries record where its *index* disagrees with its *text*,
and where the text is silent on something an ABI-compatible implementation needs. Each gap is
tracked as an open decision in `implementation-plan.md` §9.

## E2. Appendix B.10 folds libm names by suffix

B.10 lists `libm` names as families (`base`×count) after stripping one type suffix. A few
bases are folding artefacts (`cei`, `crea`, `er`, `fmu`, `isin`, `mod`: `ceil`, `creal`,
`erf`, `fmul`, `isinf`/`isnan`, `modf` with the `l` or `f` suffix removed). The family
counts still sum to the exact total (3,943 exported names). The manifest keeps family
granularity; individual `libm` names are enumerated from §10.0's suffix table when each family
is specified (phase M).

## E4. Appendix C cross-check against Appendix B

Appendix C.2 counts 3,943 distinct public names in the installed libraries' dynamic symbol
tables, which matches Appendix B exactly. Every named Appendix B symbol is present. The 311
`GLIBC_PRIVATE` names are excluded from both appendices, because they are private interfaces
between glibc's own libraries.

## E7. The thread-control-block offsets (phase 4)

Compiled code reads fixed offsets from the thread pointer: `%fs:0` (the thread pointer itself),
`%fs:0x28` (the stack-protector canary, GCC and Clang) and `%fs:0x30` (glibc's pointer guard).
Appendix A.2 names the thread-pointer register and "TLS layout expectations" without these
offsets, which every program built with `-fstack-protector` depends on. **Resolved** from the
x86-64 psABI and the compilers' documented conventions (normative references, OD-2):
`liella_rt::tls::ThreadBlock` keeps glibc's `tcbhead_t` prefix up to 0x80 and places Liella's
own fields in glibc's reserved 0x80–0x280 range (D-4.15).

## E8. The assertion message (phase 4)

§2.4 quotes the message as `Assertion 'expr' failed.`; glibc 2.39 prints
`` Assertion `expr' failed. `` (a backtick, then a straight quote), and test suites compare
against that text. **Resolved:** glibc's exact text (D-2.8).

## E9. The order of `exit`'s steps (phase 4)

§1.2 says `exit` runs the registered handlers, *then* the calling thread's `thread_local`
destructors. C++ ([basic.start.term]) requires a thread's `thread_local` objects to be destroyed
before any object with static storage duration, whose destructors are registered with
`__cxa_atexit`; glibc 2.18 and later run them first (`__call_tls_dtors` at the start of
`__run_exit_handlers`). **Resolved:** Liella runs the thread destructors first (D-1.9), as C++
programs require. Only `__cxa_thread_atexit_impl` registers such destructors, and only C++
runtimes call it.


## E10. The extracted constants table (phase 5)

Appendix C says `spec/abi/constants.tsv` holds "every integer-constant macro the public headers
define" and counts 6687. The extractor (`spec/tools/abi_extract.py`) had two faults:

* When a chunk of 400 names did not compile after one retry, it skipped the whole chunk. This
  lost 726 integer constants, among them the `_SC_*` names (glibc defines them as enumerators
  that `#define` to themselves), which `sysconf` (§24.4) needs.
* It recorded string and function-name macros (`_PATH_*`, `PRId64`, `basename`, ...) as the
  address their cast produced, which changes from run to run, and floating macros (`M_PI`) as
  their truncated value. 383 rows were such values.

**Resolved:** the extractor now bisects a failing chunk down to the offending names, rejects
floating macros by type, and keeps a value only if two runs of the probe agree (under ASLR an
address never does). `constants.tsv` was regenerated alone (`--constants-only`) on the reference
system (Ubuntu glibc 2.39-0ubuntu8.9): 7030 constants, with every value that was meaningful in
the old table unchanged. The other tables are untouched.

## E11. `waitid` reports 8 bits of exit status, not 32 (phase 11, §18.6)

Clause §18.6. An earlier text of the ⚑ note said `waitid` exposes the full 32-bit exit value in
`si_status`. The black-box record (`spec/behaviour/process.md`: `_exit(300)` gives `si_status`
44, `_exit(0x12345)` gives 69) shows the kernel hands `waitid` only the low 8 bits, the same as
`wait`/`waitpid`. The bullet "returns a `siginfo_t` with the full status" still reads loosely.
**Resolved:** Liella follows the record (D-18.4): the waits pass on what the kernel gives. The
exit status is a library-independent kernel fact, so nothing is gained by pretending otherwise.
Owner correction of 2026-10-03 already amended the ⚑ note; this entry records the disagreement.
The bullet's wording is left for the owner to amend.

## E12. The year range of `asctime` (phase 9, §23.5)

Clause §23.5. The spec said `asctime` is undefined outside years 1000-9999 and that glibc returns
`NULL` outside that range. The record (`spec/behaviour/zones.md`) shows glibc formats years 0 to
999 without padding (`... 01:03:52 0`) and fails with `EOVERFLOW` only for years below 0 and
above 9999 (`asctime_r` is probed from -1900 to 2147481747 for the fields). **Resolved:** Liella
follows the record, as glibc does; the spec text was corrected on 2026-10-02 (owner), so this
entry only records the disagreement. The 1000-9999 claim was a spec inaccuracy about the
reference, not a contract.

## E13. `ARGP_PARSE_ARGV0` counts only with `ARGP_NO_ERRS` (phase 8, §1.7)

Clause §1.7 lists `ARGP_PARSE_ARGV0` among the `argp_parse` flags and says nothing of its
condition. `<argp.h>` and the conformance probe (`conformance/c/s01_argp.c`) show that the
flag takes effect only together with `ARGP_NO_ERRS`: with both, `argv[0]` is parsed as an
element; with `ARGP_PARSE_ARGV0` alone, parsing starts at element 1 (`argv[0]` names the program in
messages). **Resolved:** Liella follows the reference (D-1.10: the flag reaches the core, and
element 0 is parsed only with `ARGP_NO_ERRS` too). The related index quirk under
both flags is a recorded difference (`docs/differences-from-glibc.md`, D-1.7). Spec text
unchanged; the owner decides whether to add the condition to §1.7.


## E11. Three stale spec statements (SPEC-AMEND-1024)

Found by probes against the reference system; amended in the spec on 2026-10-24 (owner approval,
#1992 and #2075). **Resolved 2026-10-24, spec amended.**

* §18.6, `waitid`: "the full status" is wrong; `si_status` carries 8 bits of exit status
  (SPEC-ERRATA-1024).
* §1.7, `ARGP_PARSE_ARGV0` takes effect only together with `ARGP_NO_ERRS`.
* Clause `s2_2_c_6`: `perror` makes an undecided `stderr` byte-oriented, as the reference does
  (PERROR-HERROR-REFERENCE); the spec said it stays unoriented.
