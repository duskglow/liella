#### Cross-cutting implementation decisions (not tied to one annotation)

| ID | Decision |
|---|---|
| D-X.1 | **`no_std` library.** Rust `std` is never linked into the product (§3.1). |
| D-X.2 | `Error` = `Errno` plus the internal `Canceled` marker (X1, D-22.2). |
| D-X.3 | **The kernel is a value**: library code is generic over `liella_kernel::{Sys, Machine}` (X5). This also keeps the crate graph acyclic with the boundary at both ends. |
| D-X.4 | **Zero external dependencies** (§1.2). Generated data (UCD tables, locale tables, Appendix C) is produced by project tooling from normative inputs, and the output is committed. |
| D-X.5 | Rust exports are gated behind feature `export` (`boundary::export`), and C adapters behind `LIELLA_EXPORT`, so test binaries never interpose on the host libc. |
| D-X.6 | Stable Rust. Variadic entry points and `va_arg` access are C adapters (OD-C1), so no nightly feature is needed. |
| D-X.7 | **The unsafe policy** (§2.1 S1–S4): `unsafe` only in `liella-boundary`, in four categories, each site documented and audited. Everything that needs the machine is in `csys/`. |
| D-X.8 | **Fixed-size C objects cross the boundary as `Option<&T>`/`Option<&mut T>` export parameters**, safe Rust with NULL handled by type (S6). Category *slice* is needed only for variable-length memory (buffers, strings, arrays). |
| D-X.10 | **The native Rust interface is a first-class artifact** (owner requirement 2026-10-01; mechanism decided by the owner 2026-10-02: option 3, both a stable native C ABI and a versioned Rust dylib, with a fully documented toolchain). The POSIX translation layer stays the default and C programs are unchanged; Rust programs may bypass it. **One instance of state:** a process has exactly one C library, so libc.so.6 / libc.a own every piece of process state (heap, thread blocks, `errno`, environment, current locale, time zone, streams, exit handlers). Rust data structures never cross between separately compiled objects (Rust has no stable layout), so the dividing line is: **stateful services** are reached only through the native C ABI of the library that owns the state; **stateless computation** (parsers, formatters, Unicode, calendar, math) is compiled into each Rust consumer. **Four ways in:** (1) C: the POSIX exports, unchanged. (2) **Native C ABI** (stable, any compiler): symbols `liella_<area>_<name>` exported from libc.so.6 and libc.a under version nodes `LIELLA_NATIVE_1`, `LIELLA_NATIVE_2`, ... (old nodes are never changed; additions go in a new node), with Rust-friendly C conventions: byte slices as pointer and length, no NUL termination, results as a signed value or a negative error number (no `errno`), explicit out-parameters, fixed-width types, opaque handles; described by a generated header `include/liella/native.h`. (3) **Static Rust**: the facade crate `liella-native` (`crates/native`, `#![forbid(unsafe_code)]` except its C-ABI declarations, no logic) with feature `static` re-exports the clean API (`liella`, `liella-math`, the public types of `liella-rt` and `liella-kernel`) and the stateful services as safe Rust; the program links like a product (statically, `liella-crt1.o`, libc.a, no host C library), so std's C calls and the native calls reach the same instance. (4) **Rust dylib** (toolchain-bound, versioned): `liella-native` with feature `dylib`, built as a Rust `dylib` named by its **Rust ABI version** (`libliella_rust.so.<abi>`, soname the same), containing the stateless clean API compiled by that toolchain and the stateful services as wrappers over the native C ABI, so it needs libc.so.6 and holds no state of its own; Rust ABI versions coexist in one process (different sonames). The **Rust ABI version** is `lr<N>` for the toolchain recorded in `spec/abi/rust-abi.toml` (exact rustc version and commit, target, target features, codegen options, panic strategy, std linkage, allocator), embedded in the soname, in an ELF note `.note.liella.rustabi`, and in the exported string `LIELLA_RUST_ABI`; a new toolchain or any ABI-relevant option gets a new `lr<N+1>` built beside the old ones, never in place. **lr versions are immutable** (owner ruling 2026-10-02): a released lr version is frozen permanently and never rebuilt from changed source; any change to source or toolchain, however small, requires a new lr version. `docs/toolchain.md` documents every build parameter so that a third party can build a compatible dylib or consumer without Liella's build system; `docs/interfaces.md` describes the four paths, when to use each, and the complexity they carry. **Scope of v1:** the stateful services a Rust program needs (heap, environment, file descriptors and the file system calls, clocks, the current time zone and conversions, the current locale, process exit and arguments); the stateless API is the whole clean library. Shipped with example programs for the static and dynamic paths, built and run in the gate (`cargo xtask native`). The clean API's semver policy is decided at release. **Open until the first release, Butterfly Wing (owner, 2026-10-03):** `LIELLA_NATIVE_1` and `lr1` still change (functions are added, `lr1` is rebuilt); the immutability rule begins at that release and is not yet binding. |
| D-X.11 | **Secure memory** (owner requirement 2026-10-03; `LIELLA_NATIVE_1`, open until the first release). **`liella_secure_zero(ptr, len)`** is the one zeroing implementation (`conv::secure_zero`); `explicit_bzero` and `__explicit_bzero_chk` call it (the `_chk` keeps its size check) and the heap's wipe uses it. *Guarantee:* the `len` bytes are stored as zero before the call returns, even if never read again and even when inlined or link-time optimised; not covered: copies elsewhere (registers, spills, other buffers, swap) and ordering for other threads. *Mechanism:* Rust stores, then the address is passed to OD-C1's assembly barrier (`csys/src/machine/barrier.S`), which no optimiser can see into. *Errors:* NULL with length 0 does nothing; NULL with a non-zero length, or a length above `PTRDIFF_MAX`, is `-EFAULT` (`explicit_bzero` keeps its behaviour). *Proof:* `cargo xtask native` disassembles a fat-LTO build: dead-buffer zeroing by `fill(0)` and by a wipe without the barrier is removed, while `liella_secure_zero`'s 4096-byte zeroing stays, followed by the barrier call (a planted fault makes the step fail). **`liella_heap_alloc_secure(size, align)`:** alignment, size 0 and NULL conventions as `liella_heap_alloc`; the block reads as zero. It is a large block in a mapping of its own, marked secure in the large table (length-word bit 62: a side table). Every release (`liella_heap_free`, `free`, `cfree`, `__libc_free`, `realloc`/`reallocarray`/`liella_heap_realloc` moving it or with size 0, a free from any thread, a fork child freeing its copy) zeroes the whole mapping while the releasing call owns it, then unmaps it; it is never cached, reused or moved by `mremap`, so thread-exit caches, `malloc_trim` and a fork child's parking never hold one. `realloc` keeps the block secure, in place or moved (the old block zeroed). Secure mappings get `MADV_DONTDUMP` (best effort); no `mlock` (can fail under `RLIMIT_MEMLOCK`), no `MADV_WIPEONFORK` (would change what a fork child sees). Blocks still live at exit, exec or a crash are not zeroed (the kernel reclaims the pages). *Cost:* at least a page and three system calls per secure block; nothing for small blocks; one predictable bit test per ordinary large free (heap budgets met). **liella-native:** `secure::secure_zero(&mut [u8])` and `secure::SecureVec` (a growable byte buffer in secure blocks; `truncate`/`clear` zero the removed bytes at once; `Debug` shows only the length). |
| D-X.12 | **Without `/proc` (OD-5)** (owner ruling 2026-10-04: Linux 5.10 or later with `/proc` mounted is the supported environment; a function must still never crash or give a wrong answer where `/proc` is absent, as in minimal containers and chroots, but fail with an error or use a documented fallback). Every `/proc` and `/sys` path the library opens, with its behaviour when they are absent; tested by `crates/core/tests/noproc_products.rs` (the probe `noproc_diff.c` built against glibc and statically against Liella, run as is and in a private user and mount namespace with an empty tmpfs over `/proc` and `/sys`; recorded in `spec/behaviour/noproc.md`). `get_nprocs`, `sysconf(_SC_NPROCESSORS_ONLN)` (`/sys/devices/system/cpu/online`, then `/proc/stat`): the affinity mask's count, at least 1 (as glibc). `get_nprocs_conf`, `_SC_NPROCESSORS_CONF` (`/sys/devices/system/cpu`, then `/proc/stat`): `get_nprocs` (as glibc). `sysconf(_SC_NGROUPS_MAX)` (`/proc/sys/kernel/ngroups_max`): 65536, the kernel's fixed `NGROUPS_MAX` (as glibc). `pathconf`/`fpathconf(_PC_LINK_MAX)` on the ext2/3/4 family (`/proc/self/mountinfo` tells ext4): 32000, the family's smallest limit, so a program trusting it never exceeds the real one (glibc answers the same and leaves `ENOENT` in `errno`). `pthread_getattr_np` of the initial thread (`/proc/self/maps`): `ENOENT`, as glibc (it was `ENOMEM`, which claimed an allocation failure). `pthread_setname_np`/`pthread_getname_np` of another thread (`/proc/self/task/<tid>/comm`; the calling thread's own name uses `prctl`): `ENOENT`, as glibc. `pidfd_getpid` (`/proc/self/fdinfo/<fd>`): `ENOSYS` for an open descriptor (it cannot be asked before Linux 6.13's `PIDFD_GET_INFO`), `EBADF` for one that is not open (glibc: `EBADF` for both, a wrong answer for a valid pidfd; recorded difference). `ttyname`, `ttyname_r` (`/proc/self/fd/<fd>`), and the terminal of `getlogin`, `getlogin_r`, `ttyslot` and `login` (`liella_legacy::accounting::tty_line`): the name the device number gives under the kernel's device list (Unix98 pty slaves `/dev/pts/N`, `/dev/ttyN`, `/dev/ttySN`, `/dev/tty`, `/dev/console`, `/dev/ptmx`), accepted only when that node is the very terminal (same device, inode and device number), else `ENODEV` (`term::name_by_device`; it was `ENODEV` for every terminal, and `getlogin` then reported `ENXIO`, no terminal; now as glibc on these devices). `getlogin` (`/proc/self/loginuid`): the login record of the session's terminal, as when the audit UID is unset (as glibc). `group_member` and the access checks' group test with more than 64 supplementary groups (`/proc/self/status`): the open's `ENOENT` (never a wrong yes or no); up to 64 groups use `getgroups`. `lchmod`/`fchmodat(AT_SYMLINK_NOFOLLOW)` on Linux 5.10 to 6.5 only (`/proc/self/fd`, D-13.9): `EOPNOTSUPP`, as the reference (it was `ENOENT` until 2026-10-05, found on 5.10); Linux 6.6 and later use `fchmodat2`. `closefrom` (`/proc/self/fd` only where `close_range` fails, which Linux 5.10 never does). `getauxval` and the vDSO clocks: the auxiliary vector from the process's start (`/proc/self/auxv` only in a process the library did not start, such as the hosted test harness). The name-service cache's region (`/proc/sys/kernel/random/boot_id`): a zero boot ID, so a region is not recognised across a reboot by that ID alone; lookups are unchanged (D-16.10). Not covered: `getloadavg` is covered (§24.6: it reads `/proc/loadavg` and returns -1 without `/proc`, pinned by the NO-PROC-LANE test), and paths a caller names itself (`setmntent("/proc/mounts")`, `/etc/mtab` as a link into `/proc`). **Kernels tested:** Zen 1 and Haswell-EP run 6.8.0-146; the WSL2 development kernel is 5.15.167; nothing has run on 5.10, the minimum. |
| D-X.13 | **Reloading time-zone and locale data** (owner item 2, 2026-10-04: "they stay pinned and are never reloaded under normal circumstances, but an explicit invalidation (and any case you judge necessary) must be able to reload them. Apply the same discipline as the name-service cache's invalidation", D-16.10). **Pinned:** every zone a process selects (D-23.6: parsed TZif or rule, kept with its `TZ`, `TZDIR` and file identity), every locale file mapped by path (D-7.7: category files and the archive), every parsed charmap (D-6.8), and every interned locale (D-7.8). None is ever freed or unmapped. **Explicit invalidation** (native, `LIELLA_NATIVE_1`): `liella_tz_invalidate()` and `liella_locale_invalidate()` each advance a generation counter of their own (process-wide; an atomic increment). Every pinned item records the generation it was last validated in. The first use of an item after the counter moved validates it, exactly as the name-service cache's first lookup does: the file's identity (device, inode, size, modification and change times, by `stat`) is compared with the one recorded when it was read. If it is unchanged, the item is marked current and reused, so repeated invalidations of unchanged data cost one `stat` per file and no memory. If it changed or disappeared, the file is read or mapped again (a missing file is then missing, as for a first load). `liella_tz_invalidate` then selects the zone `TZ` names at once (an explicit `tzset`: the globals are written). `liella_locale_invalidate` loads the global locale again by its current names, and keeps the old one if a name no longer resolves (`-ENOENT`). Objects from `newlocale` and `duplocale`, and threads' `uselocale` choices, keep the data they were made with: they are snapshots, and a program makes new ones. **Other cases, argued:** (1) `TZ` changed: a new selection, as before (D-23.6), no change. (2) `TZ` unset and `/etc/localtime` replaced: already seen at the next implicit `tzset`, through a `stat` on every one (§23.6, as glibc). This is the one automatic detection; making it rate-limited (one `stat` a second, as the name-service cache) would remove a system call from every `localtime`/`mktime`, but it changes observable behaviour and is the optimization thread's path, so it is left for a ruling. (3) A zone file `TZ` names replaced by a tzdata update: seen by an explicit `tzset` (as before) or after an invalidation; implicit selections stay free of system calls (pinned). (4) A locale or charmap file replaced: only after an invalidation. Locale data changes rarely and only by administration, and glibc never reloads it; a check on every `setlocale` would cost a `stat` per file for every program that switches locales. Programs that must follow an update call `liella_locale_invalidate`. **Hot path:** conversions, `ctype` and collation lookups, `nl_langinfo` and the `_l` functions are unchanged. A zone selection (already under its lock) adds one atomic load. A locale file lookup inside `setlocale`/`newlocale` (already under its lock) adds one atomic load. **Readers of old data stay safe:** nothing is unmapped or freed. A `struct tm`'s `tm_zone`, `tzname`, a `locale_t`, a cached `__ctype_b` pointer and a compiled regex keep pointing into the old, still mapped, data. **Memory bound:** one copy of a zone or locale file per distinct version a process actually loads after an invalidation (unchanged files are reused), within the caps (1,024 interned locales; 1,024 file slots and 2,048 mappings in all, D-7.7: a replaced file reuses its slot while the old mapping stays, and past the mapping cap a changed file fails to load rather than map again). **Threads:** the counters are atomics; validation and reloading happen under the existing zone and locale locks. **fork:** the child inherits the counters and the pinned data, as any memory. Both locks are already handled across `fork`. **AT_SECURE:** an invalidation reads the same paths a selection would (`TZDIR` and `LOCPATH` are ignored in secure mode as before). It is only the program's own call: no environment variable or file triggers it. **Not covered:** gettext catalogs (their own per-lookup check, D-7.5), and the `iconv` codecs built in. **Tested:** an invalidation with nothing changed reuses the data (no growth). A replaced zone file and a replaced locale file are seen after an invalidation and not before. A reload races with readers in other threads (conversions and `ctype`/`strcoll` lookups never see torn data). The state across `fork` is checked. **Measured** (Zen 1, AMD EPYC 7551, under `~/bin/timing`, 5 rounds after a warm-up, medians, libc.a before and after this change): `mktime_new_york` 443.9 to 435.1 ns, `localtime_r_new_york` 293.3 to 296.2 ns, `strcoll_utf8_16` 24.2 to 24.2 ns, `newlocale_free` 4310 to 3556 ns. Paths the change does not touch moved by -12 % to +15 % (code layout: `isalpha_c` 5.1 to 5.8 ns, `strtod_c` 92.7 to 82.0 ns), so the cost is below what this measurement resolves. |
| D-X.14 | **Overridable static library** (owner ruling 2026-10-05). `libc.a` exports its definitions as weak symbols, so a program's own strong definition wins (as with glibc's one-function objects). The library's other functions keep calling their own implementation, never a program's override, except where glibc documents the override (malloc replacement). Memory handed to the caller is allocated through the replaceable `malloc` family symbols, so a program replacing malloc frees it consistently; the same holds for preloaded allocators in phase 14. Tested by a program that defines its own copies of commonly overridden functions. **Mechanism (ledger thread, 2026-10-05):** `cargo xtask so` post-processes the archive rustc builds (`weaken_archive` in `xtask/src/so.rs`); `libc.so.6` is still linked from the unprocessed archive. (1) Every global function of every member except the replaceable allocator is renamed `__liella_libc_<name>` in its definition and in every reference in every member (`objcopy --redefine-syms`), and a weak alias `<name>` is added at the same place (`objcopy --add-symbol`): a program's strong definition of the name wins without a "multiple definition" error, and the library's own calls keep going to the library's function, because they no longer name `<name>`. (2) Data symbols are made weak in place, so a program that defines one (a documented hook such as `obstack_alloc_failed_handler`, argp's variables) shares it with the library. (3) The replaceable allocator, as the GNU C Library manual's "Replacing malloc" lists it (`malloc`, `free`, `calloc`, `realloc`, `reallocarray`, `aligned_alloc`, `malloc_usable_size`, `memalign`, `posix_memalign`, `pvalloc`, `valloc`, `cfree`), is made weak in place and never renamed: the library hands caller-owned memory out and takes it back through these symbols (`boundary::caller_alloc`), and it calls them through the C layer's one-statement forwarders `liella_caller_malloc`, `_calloc`, `_realloc` and `_free` (`csys/src/adapter/runtime.c`), because in the library's own optimised code a call to `malloc` could be inlined from, or merged with, the library's definition (observed: LLVM merged `free` with the identical `cfree`). `reallocarray` now calls `realloc` through the same path. Internal allocations a caller never frees (locale and iconv objects, the heap's own metadata) stay on Liella's allocator. Measured on the current archive: 2,651 functions renamed with aliases, 97 names weak in place. Tested by `conformance/c/x_overrides.c`: a program defines `malloc` and the rest of the family (a counting allocator over a static arena), `strlen`, `getenv`, `qsort`, `error`, `error_at_line`, `strlcpy`, `strerror` and `obstack_alloc_failed_handler`, links statically, and checks that library functions using those names internally never reach the program's copies, that its own calls do, that every caller-owned result (strdup, strndup, wcsdup, asprintf, vasprintf, getline, getdelim, open_memstream, open_wmemstream, getcwd and realpath with NULL, canonicalize_file_name, get_current_dir_name, scandir and its entries, wordexp, glob, tempnam, backtrace_symbols, reallocarray) comes from the program's allocator, that wordfree and globfree free through the program's free, and that the program's obstack handler is the one called. **Phase 14:** the same contract holds for an allocator preloaded or linked into a dynamic program: the library's caller-owned memory goes through the dynamic symbols `malloc`... (interposable), and its own calls bind to its own definitions (`-Bsymbolic`-style for everything but the allocator); to be implemented with the loader. `cargo xtask symgap` (also run by `test`, report only) lists the ABI names glibc's installed `libc.a` defines and Liella's does not, apart from those phases 14 and 15 own (2026-10-05: 132, among them `uname`, `gethostname`, `sysinfo` and the `_IO_` file internals). |
| D-X.15 | **Direct internal copies** (owner ruling 2026-10-05). The library's own memory copies and fills (the `memcpy`, `memset` and `memmove` calls rustc emits for slice copies, struct moves and fills, and the C layer's internal ones) bind directly to an internal, non-exported entry that skips the C-contract checks of the exported functions: the callers are library code whose bounds Rust already checked. Measured by PERF-REGRESS (Haswell-EP, 2026-10-05): today each such call is an indirect GOT call (`R_X86_64_GOTPCREL`, which the linker cannot relax) into the exported entry (`__liella_libc_memcpy` in `libc.a`, `memcpy` in `libc.so.6`) and its checks (`conv::move_units`), 12-16% of `snprintf` and `wordexp` time. The exported `memcpy`, `memset`, `memmove` and their checks are unchanged for programs. With D-X.14 the library's references already go to its own renamed functions, so a program's override of these names was never reached from inside the library; this ruling changes which of the library's entries they reach (and in `libc.so.6` makes the binding direct, as phase 14's `-Bsymbolic`-style binding intends). The replaceable allocator is not affected (D-X.14 (3)). **Mechanism (task INTERNAL-COPY, 2026-10-06):** the boundary crate defines the check-free entries `liella_internal_memcpy`, `liella_internal_memmove` and `liella_internal_memset` (`crates/boundary/src/conv.rs`, defined through the `internal_entry!` macro of `export.rs`: the exported bodies after their checks, `conv::move_regions`; overlap stays correct because LLVM may copy a value onto itself). `cargo xtask so` edits the archive rustc built, before both products are made from it (`xtask/src/copies.rs`): in the LTO object, every relocation naming `memcpy`, `memmove` or `memset` on a call, a jump or a load of the call target from the GOT (LLVM hoisting the target out of a loop; the library's source never takes these functions' addresses) gets the internal entry's symbol index; members that only reference the names (the C layer, `compiler_builtins`) get the undefined symbol renamed if all their uses are of those kinds; any other use is left and counted (none today). Those GOT relocations become `R_X86_64_GOTPCRELX`/`R_X86_64_REX_GOTPCRELX` (the same relocation, which stable rustc never emits), so the linker turns them into direct calls and `lea`s: in a static link, and in `libc.so.6`, whose version script keeps every `liella_` name local. **Generalised (task PJ-19, 2026-10-06; decided locally):** step 3 marks every `R_X86_64_GOTPCREL` on a call, jump or GOT load the opcode check recognises, whatever symbol it names (the relocation C compilers emit for those instructions; the linker still goes through the GOT for a name a program may interpose, so no binding changes): in `libc.so.6` the indirect `call/jmp *GOT` fell from 5798 to 47, all to exported names (`bcmp` 34, the allocator, stdio), the 1736 calls to `liella_machine_tp` among those made direct; GOT uses on other instructions (9) are left and counted. The pass refuses an internal entry that calls an internal entry or a replaced name (recursion, D-4.11). No exported symbol, version or behaviour changes; in `libc.a` the entries are renamed like every function (D-X.14). Tested by `conformance/c/x_overrides.c` (the program also defines counting `memcpy`, `memmove` and `memset`: long copies and fills inside the library never reach them, its own calls do) and unit tests of the pass and the entries; relocation counts and timings: `liella-historic:handoff/internal-copy-report.md`. Not covered: `libm.so.6`/`libm.a` (their own copies of library code are built separately). **Short copies (task PJ-20, 2026-10-07; decided locally):** library call sites with a run-time length use `liella::mem::copy`/`fill` (exactly `copy_from_slice`/`fill`): up to 32 bytes (`mem::SMALL`) two overlapping fixed-size pieces chosen by a chain of comparisons, inline, no call; longer ones the internal entries. `InlineVec::extend_from_slice`'s inline case is inlined into its callers with the same short copy; terminator stores are indexed stores (vsnprintf's NUL was `memset(p, 0, p != NULL)`); the float formatter hands digits to its sink in runs of up to 32, not one call per digit (a failing `gcvt` destination may then hold fewer partial bytes; the result is the same). The internal entries are unchanged: the `mem::` short paths may lower to `memcpy`/`memset` calls in an unoptimised build, which under the exports would recurse (D-4.11; seen as a SIGSEGV in the exports-interposed debug tests); inlining `move_regions` into them was tried and dropped (no gain on the rows measured). No unsafe added; tests at every length 0..64/96 with overlaps (`mem`, `bytes`, `conv` unit tests). Numbers: `liella-historic:handoff/smallcopy.md`. Amendment COPY-INTERNAL (2026-10-10, decided locally): the internal copy takes the export's kernel class at every size - 1-128 `hot::move_small`, 129 B-64 KiB `hot::internal_large` (AVX2 move when the kernel flag is set; before the startup decision and without AVX2 the SSE2 move, or `rep movsb` by `fallback_move`), no NULL tests (n > 0 gives valid regions); above 64 KiB `conv::copy_units`, whose non-ERMS fallback is now the AVX2/SSE2 copy instead of the byte loops (Zen 1: 64 KiB + 1 39,129 -> 5,802 instr). Zen 1 instr/call at 144 B: 141 -> 85 (export 96, glibc 41). Safety: small_copy movers + the internal-vs-memcpy sweep (0-300, 4 KiB/64 KiB, all alignments mod 32, each build, ERMS on/off); planted wrong tail red. |

| D-X.17 | **Per-thread cache words** (TB-SLOTS, 2026-10-07; inside the D-X.16 ruling: own block, fixed compile-time-checked offset, Relaxed load). `ThreadBlock::cache` is one cache line (8 `AtomicUsize` words, 0x140-0x180, inside glibc's reserved 0x80-0x280, so a block glibc's `ld.so` made has them zero) for the library's per-thread caches; owners claim words by constant in `liella_rt::tls` (`CACHE_TZ_PERIOD` = words 0-2, P7's `localtime` period, which moved out of result slot 11).
