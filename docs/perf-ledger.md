# Performance ledger (PERF-LEDGER + PERF-LEDGER-2, 2026-10-20)

Why: owner ruling 2026-10-20 for the provenance pass: code authored on or before 2026-10-02 is rewritten ("aim safe"), and the performance work done since must not be lost, so a rewrite can replicate it. This is the list of every performance improvement the repository records, with the technique, the recorded gain, the story and date, and the attempts that lost. Machine-readable twins: `bench/perf-ledger.tsv` (one row per line; `row_kind` = improvement or rejected) and `bench/perf-ledger-by-unit.tsv` (the COLD-REACH units of `liella-historic:handoff/cold-reach-units.tsv`, each with the ledger stories that touched its file).

## Method

Sources, read only (no new measurement except the spot check below): `benchmarks/progress.md` (the optimization stage: 80 before/after rows with commits); all 459 `liella-historic:handoff/reports/*.json` records (task, branch, head, one-line result); the `liella-historic:handoff/*.md` notes (rejected attempts, "do not redo" sections, files named); the dates of the report files and commit subjects on `origin/next`. A story is a row when its branch is `opt/*`, or it is a named perf/regression story, and its recorded result carries a number or a performance word. Tool, gate, flake, merge and docs stories are excluded.

PERF-LEDGER-2 additions: for every story the commits were found with `git log --numstat` (stat only, no diff text) on the story's merge into `origin/next` (`m^1..m^2`), else the merge that brought in the recorded head commit, else the recorded commit alone ("commit ... only": a partial view of a story), else the branch ref. Source files = `crates/` and `csys/` paths outside `tests/` and `benches/`, with `.md/.toml/.tsv` dropped. Four stage-1 commits that have no `progress.md` row (`e083cad`, `ed4ecf6`, `d94e7eb`, `d37d74a`) were added from their own commit messages, which carry before/after tables (see below).

Row columns: `story`, `family`, `units` (exported functions or internal unit, from a per-family map, so approximate: read the story note for the exact set), `files` (top three source files by churn of the story's commits, plus up to one more the story note names; `files_basis` says which commits), `technique` (stage-1 rows only; for story rows the technique is the first clause of `gain_as_recorded`, which is the story's own one-line result), `gain_as_recorded` (verbatim, with the row names and before/after numbers as the story wrote them; units differ between rows: instructions per call on Zen 1 for most `opt/*` stories from 2026-10-07 on, ns on Haswell-EP or Zen 1 and glibc ratios for the stage-1 and early stories), `status`, `type`, `type_kw`, `type_basis`, `src_add`/`src_del`, `date` (day the report record was added on `origin/next`; stage-1 rows: commit date), `commit`, `branch`, `cold_units_n`, `cold_units_export_match`, `cold_tiers`, `cold_units`, `note`.

`type` (PERF-LEDGER-2: **from the diff**, not the one-line result): over the story's source files, A = lines added, D = lines deleted. **rewrite** = D >= A/2 and D >= 80 and A >= 80 (the old code was replaced); **hot-path** = A >= 2D and A >= 40 (new code in front of or beside the old); **tuning** = anything smaller or in between (constant factors, ordering, alignment, placement); **no-change** = the story ended with no code or a revert (kept from the story result). `type_kw` is run 1's keyword guess from the one-line result; where the story has no source diff (`type_basis` = `kw (...)`: 37 rows, e.g. layout/page-fault stories, or stories whose branch only changed a hot-text list) `type` stays the keyword guess. This is a line-count rule, not a reading of each diff: it separates "mostly replaced" from "mostly added" well, but a new kernel added beside an old one that stays reads as hot-path, and a large refactor with an unrelated perf fix inside reads as rewrite. 158 of 312 rows changed class against the keyword guess (mostly "tuning" or "rewrite" in the story's words that the diff shows as added fast paths); the rows' `src_add`/`src_del` let a reader re-class. `status`: **reported-done** = the result line does not say WIP, checkpoint, NOT READY or NOT VERIFIED; **unfinished-or-unverified** = it does (its number may not have survived to the tree: check the commit before replicating).

COLD-REACH join (`cold_units*` columns and `bench/perf-ledger-by-unit.tsv`): a ledger row is joined to every unit of `liella-historic:handoff/cold-reach-units.tsv` whose `files` entry is one of the row's source files (**file-level join**; units are line ranges or small-function clusters of the 2026-10-02 code and the diff hunks were not intersected with those ranges, so a match says "this file carries recorded performance work", not "this unit's lines were changed"). `cold_units_export_match` counts the units that, in addition, have one of their `exports` named in the row's units, technique or result text; those are the strongest candidates (the test is a whole-word match of the export name in that text, so short common names such as `open`, `read`, `call` can match by accident: read an `export+file` row as a lead, not a proof). In the per-unit file `ledger_match` is `export+file`, `file`, or empty; `ledger_stories` lists the stories (export-matched first). Rejected attempts name no file and are not joined.

## What the sources could not tell

* **Most story rows carry one line of numbers, not a table.** The full before/after tables live in the story's own note (`liella-historic:handoff/<story>.md`) and, for the 2026-10-04/05 stage, in `benchmarks/progress.md`. Where the line gives a single "after" figure with no "before", the row says so verbatim.
* **Units are mixed and hosts differ**: stage-1 numbers are ns on Haswell-EP (Xeon E5-2697 v3) and Zen 1 (EPYC 7551); the later stories count instructions per call on Zen 1 (ptrace-counted), and sometimes cycles on the Ivy Bridge machines. Numbers from different rows are not comparable; each row is only comparable with its own glibc column.
* **Four stage-1 commits had no `progress.md` row** (`e083cad` regex overall match over flat arrays, `ed4ecf6` printf inline buffers and exact small floats, `d94e7eb` setlocale lookup cache, `d37d74a` strftime inline buffers). PERF-LEDGER-2 read their own commit messages: each has a Haswell-EP before/after table (regex 7.6-27x -> 2.8-12x of glibc, printf snprintf_e 18.6x -> 4.05x, setlocale second call 77.8 us -> 15.7 us, strftime_c_en_us 3.57x -> 2.26x), now rows `OPT-STAGE1/<sha>`. The tables are in the TSV whole for the main rows and cut for the others; the commit message has the full list.
* **Many stories have no commit hash** in the record (`head` is null or "see git log"); the `commit` column is then empty and the `branch` is the handle. Stories that were merged after rework may have changed hashes.
* **`units` is approximate** (per-family map, not per story: read the story note for the exact set). **`files` now comes from the story's commits** for 279 rows, but a branch can carry changes the perf claim does not depend on (a refactor next to the fix), and a story whose branch could not be found whole is shown from its recorded head commit only (`files_basis` says `commit ... only`); the top-churn file is not always the file where the gain is. 22 rows have no source file at all. The COLD-REACH join is file-level (hunks were not intersected with the units' line ranges, which are 2026-10-02 line numbers) and only as good as `files`.
* **Type is a line-count rule on the diff** (see Method), not a reading of each diff; 37 rows with no source diff keep the keyword guess.
* **Stories that did not finish** (status `unfinished-or-unverified`) are listed because their technique may have landed in a later story; the ledger does not trace which. Similarly a later story can supersede an earlier row (for example the three gettext, five strcmp, four mutex, six stdio, four wordexp and three strcoll rounds); the later row of a family is usually the one to replicate.
* **Gains that shrank later.** Several rows were re-measured by a later story and moved (`RC1-FIRST`, `RC2-FAULT-2`, `SEQ-REGRESS`, `NEXT-REGRESS`, `SORT-UTF8-DRIFT`, `GAWK-PRINTF` repaired regressions that a faster path introduced elsewhere). They sit in the family `regression repairs / link-level` or in their own family with the cause stated in the line.
* Nothing was found that looks like a security weakness; none is recorded.

## How to use this for the rewrite

For a unit being rewritten: find its family below, read each row newest-last, replicate the `rewrite` and `hot-path` techniques first (they carry the gains), check the `rejected` rows of the family so a failed idea is not retried, then re-measure with the story's own percall/bench rows named in the row. To find which ledger rows touch a COLD-REACH unit, look the unit up in `bench/perf-ledger-by-unit.tsv` (file-level join; `export+file` first).
