| D-4.17 | §4.3, §4.5 | — | **Bounded scanners in the C layer** (OD-C2 revised, P7; phase 6a). `memchr` uses `liella_machine_memchr`; `memcmp`, `bcmp` and `__memcmpeq` use `liella_machine_memcmp` (`csys/src/machine/scan.S`). | D-3.10 | §3.1 | — | **The heap is sharded and NUMA-aware (M1–M5).** It has 64 shards, one per NUMA node, each with its own lock, free lists, current segment and counters on its own cache lines. Segments are 16 MiB, aligned to 16 MiB, and belong to one shard; they are mapped with that shard's node preferred (`mbind(MPOL_PREFERRED)`, two internal system calls the spec does not list, since glibc does not wrap them). Slab records carry their owner shard, and `free` from any thread returns a block to its owner. The address-to-segment registry is insert-only and read without locks: segments are never unmapped, only their pages discarded. Bitmaps and use counts change only by atomic read-modify-write, so phase 6 can let other threads free without the owner's lock, without a layout change. Large blocks have their own lock, and their `mmap`/`munmap` calls run outside it. Capacity: 16 TiB of small blocks, 786,432 live large blocks, both in lazily mapped tables. Until threads know their node (phase 6), every thread uses shard 0 and placement is the kernel's default. See the NUMA review in the phase-3 Delivered block. |
| D-3.11 | §3.1 | — | **Per-thread caches are thread-owned slabs** (phase 6; M1, M2, M4, M5; design recorded before implementation by owner directive). Each thread has a *cache*: per size class a current slab and the slabs it owns, and its identifier (32 bits, never 0). A slab record gains an owner word (a cache identifier, or 0 for a slab its shard holds) and a second bitmap. **Local operations** (the owner allocating from or freeing to its own slab) touch only words the owner alone writes: the *local* bitmap and the use count, through `Relaxed` loads and stores (plain moves on x86-64: no lock prefix, no lock, no fence). Allocation is a find-first-set in the current slab's bitmap word; `free` finds the slab lock-free (the D-3.10 registry), sees its own identifier, and clears the bit after checking it was set. **Remote frees** (any other thread, or a slab no live thread owns) never write the local bitmap: they set the block's bit in the slab's *remote* bitmap (`fetch_or`; already set is a double free, a clear local bit is a double or invalid free) and count it in the slab's remote counter; the free that moves the counter from 0 pushes the slab onto the owner cache's pending list (a lock-free list the owner takes whole with one `swap`, so it has no ABA). When a current slab runs out, the owner first collects its pending slabs (`swap` each remote word to 0, clear those bits locally), then adopts a partial slab from its node's shard, then takes a new slab. A slab that becomes empty and is not current goes back to its shard. **Caches are recycled whole:** when a thread exits, its cache (with its slabs and pending list) is parked in its node's pool and the next new thread on that node takes it. A cache is never unmapped, so an identifier always names a live cache and a remote free can never reach a cache that no longer exists. **Double and invalid frees stay detected** as in D-3.10 (`Misuse`), for local and remote frees alike. The fast paths take the cache from the thread block (0x90). **`realloc` of a small block (REALLOC-FUSE, 2026-10-09, local decision under decide-or-ask; plan/heap-small.md section 7):** a block of a current slab of the caller's cache resized to at most 1 KiB (`FORECAST_CAP`) is found once through the slab-hint table, checked live (local bit set, remote bit clear: S6 exact; anything else goes to the general path, which reports the double free), kept in place when its class fits (unchanged rule: size > previous class / 2), else moved into a block from the target class's hint word and its old bit cleared as the free fast path does, without a second lookup. **Growth forecast:** a small block that `realloc` moves upward is allocated for min(2 x request, 1 KiB), so a doubling caller finds the next step in place; `malloc`'d blocks are never forecast; `malloc_usable_size` reports the larger slot (s3_1_c_7: at least the request). Memory bound: only realloc-grown blocks up to 1 KiB; their slot is at most 2.0x the unforecast slot (worst case request 512 B: 1024 vs 512) and at most 2.82x the request (17 B -> 48). |
