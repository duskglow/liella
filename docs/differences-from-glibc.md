# Differences from glibc

Liella implements the contract in `glibc-functional-spec.md`. Where the reference library
(glibc 2.39 as installed on Ubuntu 24.04, x86_64) behaves differently, and the difference is
deliberate, it is listed here with the decision that records it in `implementation-plan.md`.
Differential tests (`crates/core/tests/*_products.rs`) compare Liella with the reference library
line by line and list each of these cases; a test fails if a listed difference disappears, so
this list stays true.

Deliberate differences of scope (features not yet implemented) are in the plan's phase
Delivered blocks, not here.

| Inexact for an inexact constant of a special value (`clog(−∞ + iy)` = ∞ + iπ, `cacos(0 + i∞)`, `catan(±∞ + iy)`) | Raised. | Not raised. | D-10.14 (s10_0_f_0) |
| `errno` of a part that overflows to ±∞ or underflows to ±0, of a pole (`clog(0)`), of invalid raised by non-NaN operands (`cexp(0 + i∞)`) | `ERANGE`, `ERANGE`, `EDOM` (§10.0's rule, as for the real functions). | Not set, except incidentally (`ERANGE` for some underflows of `cexp` and `cpow`, the poles of `catan` and `catanh`). | D-10.18 (three-way: C 7.3.2 lets an implementation set `errno`; the spec's rule kept) (s10_0_f_0) |
| The sign of a part that is exactly zero where glibc returns a rounding error (`cpow(−1, 0.5)` = ±0 + i, glibc 6·10^-17 + i) | A zero (+0). | A tiny nonzero value. | D-10.17 (s10_5_c_0) |

Accuracy (D-10.3): per function and format, the fraction of results bit-identical to glibc's
and, against the test oracle (`crates/mathtools`), how many results of each side are correctly
rounded; `cargo xtask mathcmp FUNC FMT --liella`. Each milestone measures the functions it
implements; for the special functions and the wider formats still to come, glibc's own
accuracy against the oracle is the baseline. The full table is
[`libm-accuracy.tsv`](libm-accuracy.tsv) (two machines, 2026-10-04 and 2026-10-05):

* **Milestone-1 functions** (19 functions × 4 formats, every rounding direction where it
  matters, 100,000 random records per run, 30,000 for `_Float128`; 11.0 million records):
  bit-identical to glibc in every record, and every `sqrt` and `fma` result correctly rounded
  on both sides. Flags were identical as well. The exhaustive binary32 `sqrt` sweep (all 2^32 inputs, 6.5 minutes on 16 vCPUs) is bit-identical too.
* **Milestone-2 elementary functions** (`float` and `double`; `hypot` in every format): every
  Liella result in every run is correctly rounded, so every mismatch with glibc is a glibc
  result that is not.
  * binary32, exhaustive (all 2^32 inputs) in round-to-nearest for the 21 unary functions:
    bit-identical to glibc from 85.6% (`asinh`: 620 million glibc results off, up to 1.78 ulp),
    89.4% (`cbrt`) and 94.3% (`acosh`), 97–99% (`tanh`, `tan`, `sinh`, `atanh`, `log10`,
    `sin`, `cos`), to 99.5–100% for the rest (`exp`, `exp2`, `exp10`: 170,000 differences each). Downward,
    exhaustive for `exp2`, `exp10`, `expm1`, `log2`, `log10`, and every directed mode on
    1,000,000 random operands per function: 37–100% identical (mean 83%), because glibc often
    returns the round-to-nearest result there. `pow`, `atan2`, `hypot`: 100,000 random operands
    per mode; `hypot` identical in every one.
  * binary64, 100,000 random operands per function and mode: round-to-nearest 99.1–100%
    identical except `cbrt` (45.1%), `asinh` (85.2%), `tanh`, `acosh`, `sinh`, `atanh`
    (91.5–95.9%); the directed modes 24–100% (`cbrt`, `sin`, `cos`, `tan`, `atan`, `atan2`,
    `tanh`, `asinh` below 51% in some mode).
  * `hypot` of `long double` and `_Float128`: 99.1–99.99% identical, the differences glibc's.
  * Flags: identical results with different flags are glibc's inexact omissions for tiny
    arguments (for example 1.9 billion binary32 `sin` and `cos` inputs; see the table above).
* **Milestone-5a `long double` elementary functions** (20,000 random operands per function in
  round-to-nearest and 5,000 per directed mode; an earlier machine, 2026-10-05): every classified Liella
  result is correctly rounded, so every mismatch is glibc's (none where both are wrong). Round to
  nearest: bit-identical to glibc from 73.5% (`log10l`), 79.0% (`asinhl`), 85.6–86.2% (`log1pl`,
  `expm1l`, `tanhl`), 89.2–94.1% (`logl`, `sinhl`, `cbrtl`, `acoshl`, `tanl`, `atanhl`) to
  98.0–99.9% for the rest (`asinl` 99.9%, `powl` 99.5%); glibc's largest error 2.5 ulp. The
  directed modes: 4.3% (`asinhl` toward zero) to 99.6% (`atanl`), glibc's largest error 4.5 ulp.
  Up to about 10% of a directed-mode sample (operands anywhere in the format whose deviation from a
  representable value lies beyond the oracle's 4,096 bits) is undetermined; the differential
  test decides those cases on its special operands.
* **Milestone-5b `long double` special functions** (5,000 random operands per function and mode;
  an earlier machine, 2026-10-05): every classified Liella result is correctly rounded, so every mismatch
  is glibc's. Round to nearest: bit-identical to glibc 99.0% (`erfcl`), 96.3% (`erfl`), 81.5%
  (`tgammal`), 76.8% and 74.1% (`y1l`, `y0l`), 68.0% and 66.1% (`j1l`, `j0l`), 65.7%
  (`lgammal`); glibc's largest error 24 ulp (`j1l`), 20 ulp (`y0l`). The directed modes: 18.6%
  (`j0l` toward zero) to 97.1% (`erfcl` downward), glibc's largest error 311 ulp (`y0l`
  downward), 103 ulp (`j1l`). Up to 10.5% of a directed-mode sample (tiny arguments of `erfcl`,
  `j0l`, `j1l`) is undetermined by the oracle at its default precision; `special_cr.rs` and the
  differential test decide those cases at up to 65,536 bits.
* **Milestone-4a complex functions** (`float` and `double`, 2,000 random operands per function
  and format in round-to-nearest, a quarter anywhere in the finite range, `cpow`'s exponent
  within 2^±4; `complex_products.rs`, 2026-10-05): every Liella part correctly rounded, so
  every mismatch is glibc's. Both parts bit-identical to glibc: `clog` 96.3% (`double`) and
  78.4% (`float`), the inverse functions 61–79%, `cexp`, `csin`, `ccos`, `csinh`, `ccosh`,
  `ctan`, `ctanh`, `csqrt` 54–76%, `clog10` 47–53%, `cpow` 11% and 23%. The grid of special
  and boundary parts in every direction is checked line by line (no Liella error).


## Character sets (`iconv`, non-UTF-8 locales)

Charsets other than the Unicode ones, ASCII and ISO-8859-1 are read from the installed
charmaps (`/usr/share/i18n/charmaps`), where glibc uses its own conversion modules. Where the
two disagree, Liella follows the charmap (D-6.8, D-6.9):

| Case | Liella | glibc 2.39 | Clauses |
|---|---|---|---|
| Stateful encodings: ISO-2022 family, UTF-7, stateful EBCDIC | `iconv_open` fails with `EINVAL`. | Supported by modules. | `s6_4_c_3`, `s6_4_f_1`, `s6_4_g_0` |
| ANSI_X3.110-1983, ISO-IR-90, ISO_6937, T.61-8BIT | Diacritic prefixes are the private-use code points the charmap lists. | Combined with the following letter. | `s6_4_c_2`, `s6_4_g_0` |
| MAC-CYRILLIC byte `0xA2` | U+00A2 | U+0490 | `s6_4_c_2`, `s6_4_g_0` |
| GB18030 supplementary characters newer than the charmap (for example U+1F600) | Not encodable. | Mapped by the standard's arithmetic rule. Revisit if coreutils needs it. | `s6_4_c_2`, `s6_4_f_2_2`, `s6_4_g_0` |
| CP932 (WINDOWS-31J), U+2014 | Not encodable (the charmap maps `0x815C` from U+2015). | Encoded as `0x815C`. | `s6_4_c_2`, `s6_4_f_2_2`, `s6_4_g_0` |
| Names only glibc's module list gives (for example `WINDOWS-1252`) | Unknown (`EINVAL`); `CP1252` works. | Known. | `s6_4_c_1`, `s6_4_f_1`, `s6_4_g_0` |

## Candidates for cleanup

Historical glibc behaviours that Liella matches today, recorded by the owner (2026-10-02) for the
post-release pass: each could become a cleaner, consistent behaviour (and then a difference in the
table above).

| Behaviour | What Liella does now (as glibc) | Decision | Clauses |
|---|---|---|---|
| `getopt` overwriting `optopt` | `optopt` is written from the parser's state on every call (the state changes only on errors). | D-1.6 | `s1_6_f_1` |
| `getopt_long_only` with equivalent long-option entries | A prefix matching several entries with the same `has_arg`, `flag` and `val` is ambiguous for the `-`/`--` forms (not for `getopt_long`). | D-1.6 | `s1_6_i_3`, `s1_6_f_2` |
| `__printf_fp` letter mapping | Letters other than `f`/`e` use the `%g` form, with the exponent letter two below the conversion letter. | D-12.8 | `s12_11_c_4` |
| `parse_printf_format` for `%Li`/`%qi` | Reports `PA_INT` (the length modifier is not reflected). | D-12.8 | `s12_11_c_2` |
| `fts_open` options with neither or both of `FTS_LOGICAL` and `FTS_PHYSICAL` | Accepted (neither: physical; both: logical), where fts(3) says one is required. | phase 12 | `s13_3_c_4` |
| `tzset` after `TZDIR` changes with `TZ` unchanged | The explicit `tzset` re-reads `TZDIR`; the implicit one does not. | Neither reads it again (probe `tzdir_probe2.c`, liella-historic:handoff/tz-fresh.md on `fix/tz-fresh`). | owner-accepted 2026-10-09 (note: documents main's `tzset` only once `fix/tz-fresh` has landed) | `s23_6_g_0` |

Also recorded as candidates in the decision rows: `getopt`'s letter fallback searching the raw
option string (D-1.6), and `printf_size` never scaling negative values and dropping the sign of a
